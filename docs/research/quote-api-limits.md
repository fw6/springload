# 行情接口的连通性与限流实测

本文件记录从本机网络对东方财富、腾讯、新浪三家行情接口的实际请求测试。全部数据来自 2026-10-13 当天的真实请求，命令与原始返回一并列出。

## 测试环境

| 项目 | 取值 |
| --- | --- |
| 日期 | 2026-10-13（周二） |
| 本机时区 | CST，UTC+08:00 |
| 测试时间窗口 | 12:01 至 13:08（午间休市与下午交易时段） |
| 操作系统 | Darwin arm64（macOS） |
| curl | curl 8.7.1 (x86_64-apple-darwin26.0) libcurl/8.7.1 (SecureTransport) LibreSSL/3.3.6 zlib/1.2.12 nghttp2/1.69.0 |
| python3 | Python 3.13.3（仅用于解析返回内容） |

A 股连续竞价时段为 09:30–11:30 与 13:00–15:00。测试开始时本机时间为 12:01，处于午间休市，因此**午间休市时段的数据覆盖完整，上午交易时段（09:30–11:30）的数据未能覆盖**。13:00 之后的下午交易时段做了补充取样，见第四节。

curl 默认发送的请求头如下（三家接口相同，仅 Referer 需要手工添加）：

```
> GET /q=sh600519 HTTP/2
> Host: qt.gtimg.cn
> User-Agent: curl/8.7.1
> Accept: */*
```

请求节奏说明：所有连续请求测试都记录了实际起止时间，并按「请求次数 ÷ 实际耗时」计算真实速率。脚本里写的 `sleep` 间隔是两次请求之间的等待时间，真实速率还受到每次请求自身延迟的限制，因此两者并不相等。本文只采用真实速率。为避免给源站造成负担，测试没有做长时间持续加压：单次突发的规模上限为 500 次请求、50 并发，持续约 2 至 11 秒，且不同接口之间留出了间隔。

## 一、新浪 hq.sinajs.cn

### 1.1 必须携带 sina.com.cn 域的 Referer

```
$ curl -s -i --max-time 15 "https://hq.sinajs.cn/list=sh600519"
HTTP/1.1 403 Forbidden
Content-Length: 9

Forbidden
```

```
$ curl -s -i --max-time 15 -H "Referer: https://finance.sina.com.cn" "https://hq.sinajs.cn/list=sh600519"
HTTP/1.1 200 OK
Cache-Control: no-cache
Content-Length: 273
Connection: Keep-Alive
Content-Type: application/javascript; charset=GB18030

var hq_str_sh600519="����ę́,1287.000,1288.000,1279.230,1288.480,1273.180,1279.220,1279.990,1292370,1655329939.000,100,1279.220,800,1279.210,200,1279.200,100,1279.080,100,1278.900,200,1279.990,3400,1280.000,200,1281.210,300,1281.240,300,1281.270,2026-10-13,11:30:00,00,";
```

返回内容使用 GB18030 编码，`Content-Type` 里也写明了 `charset=GB18030`。用 UTF-8 直接显示股票名称会乱码，需要转码，例如 `iconv -f GB18030 -t UTF-8`。转码后：

```
var hq_str_sh600519="贵州茅台,1287.000,1288.000,1279.230,1288.480,1273.180,1279.220,1279.990,1292370,1655329939.000,100,1279.220,800,1279.210,200,1279.200,100,1279.080,100,1278.900,200,1279.990,3400,1280.000,200,1281.210,300,1281.240,300,1281.270,2026-10-13,11:30:00,00,";
```

不带 Referer 时返回 HTTP 403 与 9 字节的纯文本 `Forbidden`，没有任何 JSON 或行情内容。

### 1.2 Referer 的匹配规则

对不同 Referer 取值逐个测试（每次请求只改 Referer）：

| Referer 取值 | 返回状态码 |
| --- | --- |
| 不带 Referer | 403 |
| `Referer:`（空值） | 403 |
| `https://finance.sina.com.cn` | 200 |
| `https://finance.sina.com.cn/` | 200 |
| `https://www.sina.com.cn` | 200 |
| `https://sina.com.cn` | 200 |
| `https://foo.sina.com.cn` | 200 |
| `http://finance.sina.com.cn` | 200 |
| `https://evil.example.com` | 403 |
| `https://notsina.com.cn` | 403 |
| `https://xsina.com.cn` | 403 |
| `https://sinacom.cn` | 403 |
| `https://sina.com.cn.evil.example.com` | 403 |
| `https://finance.sina.com.cn.evil.example.com` | 403 |
| `https://sina.com.cn:8443` | 403 |
| `not a url at all` | 403 |

从这张表可以判定，校验针对 Referer 里的主机名：主机名等于 `sina.com.cn` 或者是它的子域（以 `.sina.com.cn` 结尾）时通过，协议 http 与 https 都接受。字符串包含关系不通过——`notsina.com.cn`、`xsina.com.cn` 都是 403；把 `sina.com.cn` 放在主机名前面再加别的域（`sina.com.cn.evil.example.com`）也是 403。Referer 里带端口号（`sina.com.cn:8443`）也是 403。

### 1.3 User-Agent 没有影响

| User-Agent | Referer | 返回状态码 |
| --- | --- | --- |
| curl/8.7.1（默认） | 无 | 403 |
| `Mozilla/5.0` | 无 | 403 |
| 空 | 无 | 403 |
| curl/8.7.1（默认） | `https://finance.sina.com.cn` | 200 |
| `Mozilla/5.0` | `https://finance.sina.com.cn` | 200 |
| 空 | `https://finance.sina.com.cn` | 200 |

User-Agent 取任何值都不改变结果，起决定作用的只有 Referer。

### 1.4 连续请求与封禁表现

所有测试都带合法的 `Referer: https://finance.sina.com.cn`，请求 `/list=sh600519`。

| 测试方式 | 请求次数 | 实际耗时 | 真实速率 | 结果 |
| --- | --- | --- | --- | --- |
| 串行，间隔 0.25 秒 | 40 | 16 秒（12:03:20–12:03:36） | 约 2.4 次/秒 | 全部 200 |
| 串行，间隔 0.05 秒 | 100 | 23 秒（12:07:41–12:08:04） | 约 4.3 次/秒 | 全部 200 |
| 串行，间隔 0.02 秒 | 200 | 40 秒（12:10:15–12:10:55） | 约 5.0 次/秒 | 全部 200 |
| 20 并发 | 200 | 2 秒（12:12:53–12:12:55） | 约 100 次/秒 | 全部 200 |
| 50 并发 | 500 | 2 秒（12:15:20–12:15:22） | 约 250 次/秒 | 全部 200 |

每轮测试结束后按递增间隔继续探测（+5 秒、+15 秒、+30 秒、+60 秒、+120 秒、+300 秒，最长探测到 +300 秒），全部返回 200。

在本次测试覆盖的强度范围内（最高 500 次请求、50 并发、约 250 次/秒），**没有观察到任何限流或封禁**：没有出现 403、429、连接重置，也没有出现返回内容变短或数据为空的情况。更高的速率与更长的持续时间是否会触发封禁，**未能核实**。

### 1.5 批量代码

`list` 参数支持逗号分隔的多只代码，例如 `list=sh600519,sh600000`。分号与空格都不被识别为分隔符（`list=sh600519;sh600000` 会被当成一个整体，返回空条目）。

| 请求代码数 | URL 长度（字符） | 返回状态码 | 返回条目数 |
| --- | --- | --- | --- |
| 2 | 43 | 200 | 2 |
| 50 | 475 | 200 | 50 |
| 200 | 1825 | 200 | 200 |
| 500 | 4525 | 200 | 500 |
| 850 | 7675 | 200 | 850 |
| 890 | 8035 | 200 | 890 |
| 900 | 8125 | 431 | 0 |

上限在 8035 字符（890 只）与 8125 字符（900 只）之间。超出后返回 HTTP 431：

```
$ curl -s -i --max-time 20 -H "Referer: https://finance.sina.com.cn" "https://hq.sinajs.cn/list=sh600000,...,sh600899"
HTTP/1.1 431 Request Header Fields Too Large
Content-Length: 10

Big header
```

与腾讯省略缺失代码不同，新浪会为不存在的代码返回一条空占位：

```
var hq_str_sh600013="";
var hq_str_sh600519="贵州茅台,1287.000,1288.000,...";
```

这意味着新浪的返回条目与请求代码是**一一对应且顺序一致**的，可以直接按下标取值；腾讯则必须按返回的代码字段重新配对。

### 1.6 三家的 URL 长度上限对比

三家接口的上限都在 8 KB 附近，与常见的 nginx `large_client_header_buffers` 默认值 8k 相符。这一对应关系属于推断，服务端的实际配置无法从外部核实。

| 数据源 | 协议 | 通过的最大 URL 长度 | 失败的最小 URL 长度 | 失败返回 |
| --- | --- | --- | --- | --- |
| 新浪 hq.sinajs.cn | HTTP/1.1 | 8035 字符 | 8121 字符 | 431 Big header |
| 腾讯 qt.gtimg.cn | HTTP/1.1 | 8121 字符 | 8571 字符 | 414 Request-URI Too Large |
| 腾讯 qt.gtimg.cn | HTTP/2 | 5691 字符 | 5736 字符 | 连接层拒绝，curl 退出码 16 |
| 东方财富 push2 | HTTP/1.1 | 8179 字符 | 8404 字符 | 502 Bad Gateway |

## 二、腾讯 qt.gtimg.cn

### 2.1 请求头与协议

| 条件 | 返回状态码 |
| --- | --- |
| 默认（curl UA，无 Referer） | 200 |
| User-Agent 为空 | 200 |
| User-Agent `Mozilla/5.0` | 200 |
| `Referer: https://gu.qq.com` | 200 |
| `Referer: https://evil.example.com` | 200 |
| 走 HTTP/2 | 200 |
| 走 HTTP/1.1 | 200 |
| 明文 `http://` 访问 | 200 |

腾讯接口不校验 Referer，也不校验 User-Agent，HTTP 与 HTTPS 都可用。默认走 HTTP/2。

### 2.2 单次请求可携带的代码数量

请求形式为 `https://qt.gtimg.cn/q=sh600519,sh600000,...`，代码之间用逗号分隔。

| 请求代码数 | 协议 | URL 长度（字符） | 返回状态码 | 返回字节数 | 返回条目数 |
| --- | --- | --- | --- | --- | --- |
| 1 | HTTP/2 | 44 | 200 | 504 | 1 |
| 50 | HTTP/2 | 479 | 200 | 18204 | 37 |
| 200 | HTTP/2 | 1838 | 200 | 84964 | 177 |
| 500 | HTTP/2 | 4523 | 200 | 202619 | 423 |
| 630 | HTTP/2 | 5691 | 200 | 261135 | 未统计 |
| 635 | HTTP/2 | 5736 | 失败 | 0 | 0 |

50 只、200 只、500 只都可以一次请求拿到，返回 HTTP 200。触发拒绝的条件是 URL 长度，与代码数量无关，而且**HTTP/2 与 HTTP/1.1 的上限完全不同**：

| 请求代码数 | 协议 | URL 长度（字符） | 返回状态码 | 返回字节数 |
| --- | --- | --- | --- | --- |
| 635 | HTTP/2 | 5736 | 失败（curl 退出码 16） | 0 |
| 700 | HTTP/1.1 | 6321 | 200 | 293872 |
| 700 | HTTP/2 | 6321 | 失败（curl 退出码 16） | 0 |
| 800 | HTTP/1.1 | 7221 | 200 | 341636 |
| 900 | HTTP/1.1 | 8121 | 200 | 388330 |
| 950 | HTTP/1.1 | 8571 | 414 | 169 |
| 1000 | HTTP/1.1 | 9021 | 414 | 169 |

用 HTTP/2 时，URL 长度到 5736 字符（635 只代码）就被拒绝，curl 退出码 16（HTTP/2 协议层错误），TCP 连接本身是建立成功的，是请求头被拒。用 HTTP/1.1 时，同样的 700 只代码能正常返回 200，上限在 8121 字符（900 只）与 8571 字符（950 只）之间，超出后返回 HTTP 414。

HTTP/1.1 下超出上限的完整返回：

```
$ curl -s -i --http1.1 --max-time 30 "https://qt.gtimg.cn/q=sh600000,...,sh600999"
HTTP/1.1 414 Request-URI Too Large
Server: stgw
Date: Tue, 13 Oct 2026 04:06:00 GMT
Content-Type: text/html
Content-Length: 169
Connection: close

<html>
<head><title>414 Request-URI Too Large</title></head>
<body>
<center><h1>414 Request-URI Too Large</h1></center>
<hr><center>stgw</center>
</body>
</html>
```

对于业务代码来说，500 只代码一次请求（HTTP/2 下 4523 字符）留有很大余量；如果必须一次携带更多，改用 HTTP/1.1 可以带到 900 只左右。

### 2.3 不存在的代码会被整条省略

腾讯对不存在的代码不返回任何条目。这一点在拼接代码列表时必须处理，否则无法把返回结果与请求顺序对应起来。

请求 `sh600000` 到 `sh600049` 共 50 个代码，实际返回 37 条，缺失的 13 个是：

```
sh600013 sh600014 sh600024 sh600034 sh600040 sh600041 sh600042 sh600043 sh600044 sh600045 sh600046 sh600047 sh600049
```

请求 200 个代码返回 177 条（缺失 23 个），请求 500 个代码返回 423 条。返回内容里没有出现形如 `v_sh600013="";` 的空条目，缺失代码完全不出现。

### 2.4 每分钟一次、持续一小时

测试方式：固定请求 50 个代码（`sh600000` 至 `sh600049`），每轮之间间隔 60 秒，共 60 轮，从 12:01:49 持续到 13:01:03。

60 轮全部返回 HTTP 200，没有任何一轮被拒绝，也没有出现限流提示或返回变空。整轮测试跨越了午间休市与下午开盘。完整统计见附录 B.1。

### 2.5 瞬时并发

在一小时轮询结束之后执行，500 次请求、50 并发，约 250 次/秒，全部返回 HTTP 200。完整结果见附录 B.2。

### 3.3 push2his.eastmoney.com 历史 K 线

```
$ curl -s --max-time 15 "https://push2his.eastmoney.com/api/qt/stock/kline/get?secid=1.600519&fields1=f1,f2,f3,f4,f5,f6&fields2=f51,f52,f53,f54,f55,f56,f57,f58&klt=101&fqt=1&beg=20260901&end=20500101"
{"rc":0,"rt":17,"svr":183124298,"lt":1,"full":0,"dlmkts":"","dsc":"0","data":{"code":"600519","market":1,"name":"贵州茅台","decimal":2,"dktotal":6019,"preKPrice":-313.3,"klines":["2026-09-01,1295.00,1299.56,1307.99,1286.10,..."]}}
```

`klt` 是 K 线周期（101 为日线），`fqt` 是复权方式。**`lmt` 参数无效**：分别传 `lmt=10`、`lmt=100`、`lmt=1000`、`lmt=10000`、`lmt=100000`，返回内容完全相同，都是 413976 字节、6019 条记录（`dktotal` 为 6019）。控制返回区间要用 `beg` 与 `end`：

| 参数 | 返回字节数 | 首条记录日期 |
| --- | --- | --- |
| `lmt=10`，`beg=0` | 413976 | 2001-08-27 |
| `lmt=1000`，`beg=0` | 413976 | 2001-08-27 |
| `beg=20260901`，`end=20500101` | 1936 | 2026-09-01 |

只传 `beg` 与 `end` 就能把返回控制在需要的区间，`lmt` 不起作用。

## 四、交易时段与非交易时段的差别

对同一只股票（`sh600519` 贵州茅台）在三个数据源上取样，比较休市与开市时的字段表现。

### 4.1 午间休市取样（12:11:19）

| 数据源 | 关键字段 | 取值 |
| --- | --- | --- |
| 腾讯 | 字段 30（时间） | `20261013120538`（2026-10-13 12:05:38） |
| 腾讯 | 当前价 | 1279.23 |
| 新浪 | 日期 / 时间 | 2026-10-13 / 11:30:00 |
| 新浪 | 当前价 | 1279.230 |
| 东方财富 | `f86`（时间戳） | 1791864668（2026-10-13 12:11:08） |
| 东方财富 | `f43`（当前价，放大 100 倍） | 127923 |

三家返回的价格一致（1279.23），差别在时间字段：

- 新浪的 `date` / `time` 是**最后一笔成交的时间**，休市期间固定为 11:30:00，即上午收盘时刻。
- 腾讯的字段 30 在休市期间停在 12:05 前后的刷新时刻，与上午收盘时刻（11:30:00）和本机当前时间都不相同，各只股票的取值互不相同：

  | 代码 | 字段 30 | 当前价 |
  | --- | --- | --- |
  | sh600519 | 20261013120538 | 1279.23 |
  | sh600000 | 20261013120548 | 9.65 |
  | sz000001 | 20261013120542 | 11.66 |
  | sh601318 | 20261013120532 | 52.43 |
  | sz300750 | 20261013120515 | 289.65 |
  | sh688111 | 20261013120531 | 230.30 |

  连续三次请求同一只股票（12:15:31、12:15:43、12:15:55），字段 30 都停在 `20261013120538` 不变。
- 东方财富的 `f86` 是**服务器处理请求的时间**，与本机时间只差几秒。

### 4.2 下午交易时段取样

13:01 至 13:06 之间对同一只股票取样四次，明细见附录 C。要点：

- 开市后三家返回的价格都在跟随成交变动，不再固定在上午收盘价。
- 三个数据源的时间字段都跟上了本机时间：腾讯的字段 30 与本机时间相差 2 至 4 秒，新浪的时间与本机时间相差 1 秒以内，东方财富的 `f86` 与本机时间相差 1 至 2 秒。
- 同一时刻取样（13:07:55 至 13:08:09，间隔 3 秒取五次）中，腾讯与新浪的价格在每一轮完全一致；东方财富的价格与它自己的 `f86` 时间戳对应，可能领先几秒，数值上会有几分钱的差别。逐次取样见附录 C.2。

### 4.3 休市与开市的差别对照

| 项目 | 午间休市 | 下午交易时段 |
| --- | --- | --- |
| 新浪 `time` 字段 | 固定在 11:30:00（上午收盘时刻） | 跟随当前成交时间 |
| 腾讯字段 30 | 停在 12:05 前后的刷新时刻，各股不同 | 跟随当前时间，落后 2 至 4 秒 |
| 东方财富 `f86` | 服务器当前时间 | 服务器当前时间 |
| 三家价格 | 完全相同，为上午收盘价 | 腾讯与新浪完全相同；东方财富与自己的 `f86` 对应，可能领先几秒 |
| 请求成功率 | 全部 200 | 全部 200 |

三家的接口在休市期间都继续正常响应，返回的是最后一笔成交的快照，没有出现空数据或错误码。休市与开市对**连通性与限流没有观察到差别**，差别只在时间字段的含义上。

## 五、未能核实的问题

1. **新浪的封禁阈值**。本次测试最高到 500 次请求、50 并发（约 250 次/秒），全部返回 200。触发封禁所需的速率与持续时间未能核实；封禁后的恢复时间也未能核实，因为测试中没有触发过封禁。
2. **腾讯的封禁阈值**。本次测试最高到 500 次请求、50 并发（见附录 B），全部返回 200。触发封禁所需的速率与持续时间未能核实，恢复时间也未能核实。
3. **东方财富的限流阈值**。本次测试最高到 500 次请求、50 并发（约 250 次/秒），全部返回 200，`rc` 均为 0。触发限流的阈值与恢复时间未能核实。
4. **上午交易时段（09:30–11:30）**。测试从 12:01 开始，该时段未能覆盖。
5. **东方财富 `secid` 的市场前缀覆盖范围**。本次只用了上海（`1.`）与深圳（`0.`），其他市场（如北交所、港股、美股）未测试。
6. **接口的长期稳定性与数据准确性**。本次测试只覆盖单日的一个下午，不涉及长期可用性与数据质量。
7. **`http://` 明文访问 push2his**。只测了 push2 的明文访问，push2his 的明文访问未测试。
8. **东方财富除 `stock/get`、`ulist.np/get`、`stock/kline/get` 之外的其他接口**。本次未测试。
