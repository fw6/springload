# 通达信行情源实测

对应改造：把日线、分钟线与除权除息从东方财富接口换成通达信协议。协议解析用
`rustdx-complete` 1.11.0（MIT）。全部结论来自 2026-10-15 当天从本机发起的真实请求，
命令与原始返回一并列出。

调查环境：macOS arm64，CST，Python 3.13.3（pytdx 1.72 作对照实现），
`rustdx-complete` 1.11.0。

`pytdx` 内置 104 台行情服务器（`pytdx.config.hosts.hq_hosts`），逐台发起
`get_security_bars(9, 1, "600519", 0, 5)`：

```
    117.34.114.14:7709 国泰君安 K线 5 快照 1 xdxr 45 列表 0
    117.34.114.15:7709 国泰君安 K线 5 快照 1 xdxr 45 列表 0
    117.34.114.16:7709 国泰君安 K线 5 快照 1 xdxr 45 列表 0
    117.34.114.17:7709 国泰君安 K线 5 快照 1 xdxr 45 列表 0
    117.34.114.18:7709 国泰君安 K线 5 快照 1 xdxr 45 列表 0
    117.34.114.20:7709 国泰君安 K线 5 快照 1 xdxr 45 列表 0
    117.34.114.27:7709 国泰君安 K线 5 快照 1 xdxr 45 列表 0
能建立连接的: 33 台
连接成功但 K 线为空的样例: [('180.153.18.170:7709', 0, 45, 0), ('218.75.126.9:7709', 0, 45, 0), …]
```

33 台能建立 TCP 连接，只有 8 台能返回 K 线与快照，全部在国泰君安同一网段
（117.34.114.13 至 117.34.114.27）。**TCP 连得上不等于能出数据**，所以服务器必须
按「能不能返回 K 线」来挑，不能按连接是否成功来挑。

请求类型逐项核对（同一批服务器）：

```
==================== 国泰君安 117.34.114.15
   日线 category=9 沪市 start=0: 5 条
   日线 category=4 沪市 start=0: 5 条
   日线 category=9 深市: 5 条
   指数日线 1.000001: 5 条
   5分钟 category=0: 5 条
   当日分时: 165 条
   历史分时 20261015: 165 条
   快照: 1 条
   xdxr: 45 条
   列表一页: 0 条
==================== 上海电信主站Z1 180.153.18.170
   日线 category=9 沪市 start=0: 0 条
   当日分时: 165 条
   历史分时 20261015: 165 条
   快照: 0 条
   xdxr: 45 条
   列表一页: 0 条
```

分时（`get_minute_time_data`）在所有能连的服务器上都能取；K 线与快照只在国泰君安那
8 台上能取。`pytdx` 的 `get_security_list` 在国泰君安上返回空，而 `rustdx-complete`
的 `stocks()` 在同一台机器上能取回全量（深市 24452 条、沪市 27459 条），两者的分页
实现不同。

`rustdx-complete` 内置的 `STOCK_IP` 有 40 台，实测这 40 台全部能返回 xdxr 与列表，
K 线与快照一律为空——它内置的列表里没有一台能出数据。所以服务器清单由本仓库自己维护，
见 `market/tdx.rs` 的 `SERVERS`。

## 二、字段与单位

日线（`category=9`）返回 `open`、`close`、`high`、`low`、`vol`、`amount` 与日期时间。
成交量单位随周期变化，用 `amount / (vol * close)` 判定：

```
=== 日线 vol 单位判定 ===
  600519 2026-10-15 vol=40227 close=1306.2 amount=5252224512 amount/(vol*close)=99.958
  000001 2026-10-15 vol=1064235 close=11.3 amount=1210942848 amount/(vol*close)=100.695
=== 各分钟周期 vol 单位判定 ===
  1分钟 2026-10-15 13:46 vol=3400 close=1306.2 amount=4440173 比值=1.000
  5分钟 2026-10-15 13:50 vol=3400 close=1306.2 amount=4440173 比值=1.000
  15分钟 2026-10-15 14:00 vol=3400 close=1306.2 amount=4440173 比值=1.000
  30分钟 2026-10-15 14:00 vol=184200 close=1306.2 amount=239865968 比值=0.997
  1小时 2026-10-15 14:00 vol=582700 close=1306.2 amount=759380608 比值=0.998
```

比值约 100 表示成交量是手，约 1 表示是股。**日线是手（要乘 100 换算成股），分钟线是股。**
成交额两家都是元。`rustdx-complete` 的 `KlineData.vol` 文档写的是「单位：股」，与实际
不符，换算由本仓库自己做。

分钟周期的 `category` 取值：1 分钟 7、5 分钟 0、15 分钟 1、30 分钟 2、60 分钟 3。
`category` 7 与 8 都返回 1 分钟 K 线。

## 三、除权除息与前复权

`xdxr` 返回的记录里 `category=1` 是除权除息，字段是每 10 股派现金（`fh_qltp`）与每
10 股送转股（`sg_hltp`），除以 10 得到 `CorporateAction` 要的每股口径。协议不提供
除权日的前收盘价，由不复权日线里除权日前最后一根的收盘价按参考价公式算出。

拿仓库 `adjustment.rs` 的公式（`P ↦ (P − D) / (1 + r)`，事件按除权日升序）从
通达信不复权日线推算前复权，与腾讯前复权（`web.ifzq.gtimg.cn` 的 `qfq` 序列）对照：

```
code | 重叠天数 | 最大偏差 | 偏差最大的日期 | 本地 | 腾讯
600519 | 641 | 0.077 | 2024-06-19 | 1397.46 | 1397.537
000001 | 641 | 0.005 | 2025-06-13 | 10.74 | 10.735
300750 | 641 | 0.103 | 2024-02-22 | 140.16 | 140.263
601318 | 641 | 0.039 | 2024-02-22 | 35.97 | 36.009
601899 | 641 | 0.000 | 2024-02-22 | 11.66 | 11.66
```

15 只股票、641 个重叠交易日，最大偏差 0.103 元。逐条改写成「每步取整」不改变这个
偏差（600519 从 0.077 变成 0.071，其余不变），说明差异来自腾讯自己的复权算法，
不是本仓库的取整时机。

与库里存着的东方财富前复权对照（25 只沪市主板股票、726 个重叠交易日）：

```
600519: 重叠 726 天，最大偏差 8.00（2026-10-14 本地 1286.0 vs 库里 1278.0）
601318: 重叠 726 天，最大偏差 0.09（2026-10-14 本地 51.23 vs 库里 51.32）
600276: 重叠 726 天，最大偏差 0.01（2026-10-14 本地 45.49 vs 库里 45.48）
601899: 重叠 726 天，最大偏差 0.15（2026-10-14 本地 29.98 vs 库里 30.13）
```

偏差最大的日期全部是 2026-10-14，也就是库里那一行本身有问题（见第五节）。除它之外
最大偏差在 0.02 元以内。

`rustdx-complete` 自带的 `k_adjusted(Adj::Qfq)` 精度不够：600519 偏差 27.28 元、
300750 偏差 9.27 元、000858 偏差 5.14 元。复权要用仓库自己的公式。

## 四、吞吐与服务器行为

单连接顺序取数（日线一页 800 根 + xdxr）：

```
连续 200 次 k(): 9.3 秒，共 145228 根，空 0 只
连续 200 次 xdxr: 8.8 秒，共 8402 条，空 0 只
```

每只约 90 毫秒，3398 只沪深主板股票单连接约 5 分钟。8 条连接并行时每只 17 毫秒，
全市场约 1 分钟。

三处要绕开的坑：

- **`k_batch` 不沿用指定的主机配置。** 同一个 client 上 `k(1, "600519")` 返回 727 根，
  而 `k_batch(&[(1, "600519")])` 返回 `Ok(0)`；对 3398 只批量拉取全部为空。并发要自己
  开线程用 `k()`，不能用 `k_batch`。
- **突发之后服务器静默返回空。** 连续 30 次 xdxr 加一次全量列表之后，同一进程里后续
  200 只的 xdxr 全部返回空；换新连接、隔一段时间重跑同样的 200 只则全部正常
  （8402 条记录，零空）。空结果与「本来就没有数据」无法从返回值区分，`rustdx-complete`
  的 `recheck_empty` 只覆盖 K 线区间拉取，xdxr 没有这层保护。
- **退市代码返回空而不是报错。** `bars_range(1, "600001", 9, …)` 返回 0 根。回补只遍历
  证券列表里的代码，所以空结果按故障处理。

## 五、全市场回补与逐行核对

以 3127 只沪深主板股票为池，回补三年日线：2,291,729 根，耗时 83 秒（6 条连接），
无失败。把这批数据与库里现存的东方财富前复权逐行比对（1,465,200 个重叠的
`(代码, 日期)`）：

```
重叠 1465200 行（已排除 2026-10-14）
  最大偏差超过 0.001 元的股票：470 只
  最大偏差超过 0.01 元的股票：460 只
  最大偏差超过 0.1 元的股票：33 只
  最大偏差超过 0.5 元的股票：6 只
  最大偏差超过 1 元的股票：4 只
  最大偏差超过 2 元的股票：2 只
```

成交量与成交额逐行一致：不含 2026-10-14 时成交量的最大绝对差是 300 股（取整），
成交额的最大相对差是 0.000000。

偏差超过 0.1 元的 33 只做三方对照（本地推算 / 腾讯前复权 / 库里），分成三类：

```
分类结果：{'本地与腾讯一致（库陈旧）': 10, '腾讯与库一致（通达信漏事件）': 9, '三方都不一致': 14}
```

- **10 只是库里陈旧。** 本地推算与腾讯一致（偏差 0.001 至 0.025 元），库里与两者都
  不一致，差在最近一次分红上。例如 601766 窗口内有 2025-11-20 每 10 股派 1.1 元，
  库里 2025-11-20 之前的历史没有减掉这 1.1 元。
- **9 只是通达信的除权记录不完整。** 腾讯与库里一致，本地推算缺了调整：
  603007（差 5.69 元）、603559（4.42）、600165（1.57）、600715（0.54）、
  600375（0.46）、002768（0.40）、003010（0.40）、603281（0.24）、603237（0.19）。
  这些是重整转增类个股：不复权价格在除权日真的跳了一大截，而通达信的 `xdxr` 要么
  没有 `category=1` 记录（603559 的 2024-12-26 只有 `category=9 转配股上市` 与
  `category=15`），要么记录的比例对不上（603007 的 2024-12-26 记每 10 股转增 1.5535 股，
  实际价格跳了约 1.77 倍）。协议里没有除权参考价，没法从价格反推，这一项没有在本仓库
  里补救。
- **14 只三方都不一致**，量级在 0.1 至 0.3 元，属于不同行情源各自的复权取整差异。

### 陈旧历史是怎么来的

库里的前复权历史由回补写入。回补的增量路径从最后一条日线开始取数，除权日之前的历史
不会重取，只能靠过期检查触发重算。原来的过期判据是「最近一次除权除息日晚于本地最后
一条日线」——同步发生在除权日之后时，除权日早于最后一条日线，这段历史就永远停在旧价
上，601766 那 1.1 元就是这么漏掉的。

现在的判据改成比对事件集合：刚取到的事件里只要有一天不在 `corporate_action` 表里，
或者同一天的分红送配比例与表里不同，就判过期。库里多出来的事件不触发重算，避免每次
检查都重复重算。

### 列表里有、取不到日线的代码

第一次回补时有 50 只报「取不到日线」（001381、000003、000004、000005、000015 等）。
通达信的证券列表里留着已退市与长期停牌的代码，它们返回 0 根日线而不是报错，所以空
结果按「不进股票池」处理。为免整台服务器不出数据时被静默跳过，全市场一只都没取到
日线时同步整体报错。

## 六、顺带发现的东方财富问题

从本机对东方财富三个接口各发三次请求：

```
K线接口: 3 次中成功 0，失败原因 ['RemoteDisconnected', 'RemoteDisconnected', 'RemoteDisconnected']
列表接口: 3 次中成功 1，失败原因 ['RemoteDisconnected', 'RemoteDisconnected']
分红接口: 3 次中成功 3，失败原因 []
```

K 线接口连续三次被对端断开，这就是改换数据源的起因。`datacenter-web.eastmoney.com`
的分红接口正常，说明拒绝按主机与路径区分。

库里 `stock` 表 3213 只主板股票中有 1140 只没有日线，其中 1003 只在通达信的证券列表
里存在（换源后可以补齐），137 只是已退市或已合并的代码（招商地产、石油大明、绿景退、
退市太和等），东方财富的列表里有而通达信没有。

库里的 2026-10-14 那一行与通达信、腾讯都不一致：600519 收盘 1278.0 对 1286.0，
成交量 530,700 股只有正常日的两成。同一现象出现在全部 25 只抽查股票上，是盘中残缺
快照在收盘后没有被改写。

## 七、akshare 与 pytdx 的定位

两者都只当作地址与字段的参考，不引入依赖。

Python 版 `akshare` 1.19.1（MIT，仓库 `akfamily/akshare`）的东财系函数在本机全部失败
（`stock_zh_a_hist`、`stock_zh_a_hist_min_em`、`stock_zh_a_spot_em`、`stock_sh_a_spot_em`、
`stock_bid_ask_em` 都是连接被对端关闭），能用的只有新浪与东财 datacenter 两条通路。
它的新浪日线需要 `mini-racer` 起 JS 引擎解码 `klc_kl.js`，而且用的是等比复权因子，
与东财、腾讯、仓库现有公式的减法口径不一致：600519 在 2023-11-06 相差 30.71 元。

`pytdx` 1.72 在 Python 3.13 上能装能跑，但仓库 `rainx/pytdx` 的 `archived` 为 `true`、
最后一次提交 2020-04-15、没有 LICENSE 文件，README 声明「用于个人对网络协议的研究和
习作，不对外提供服务」「机构请不要使用此代码」。它是 Python 库，接进 Rust 的 Tauri
应用要额外带一个 Python 运行时。

可以直接在 Rust 里实现的另外两个地址（本次改造没有采用）：

- 腾讯日线 `proxy.finance.qq.com/ifzqgtimg/appstock/app/newfqkline/get`，参数
  `param=sh600519,day,,,800,qfq`，返回 801 行、覆盖 2023-06-26 至 2026-10-15，
  第 8 项是换手率、第 9 项是成交额（万元）；`count` 传 1200 或 2000 都只回 641 行。
  仓库 `tencent.rs` 现在打的是 `web.ifzq.gtimg.cn/appstock/app/fqkline/get`，
  那个只回 6 个字段、没有成交额。
- 新浪分钟线 `quotes.sina.cn/cn/api/jsonp_v2.php/=/CN_MarketDataService.getKLineData`，
  参数 `symbol=sh600519&scale=1&ma=no&datalen=1970`，纯 JSONP，不需要 JS 解码。
